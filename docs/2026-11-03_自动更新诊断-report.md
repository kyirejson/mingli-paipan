# v1.0.13 无法发现 v1.0.14 的原因

观察日期：2026-11-03（Asia/Shanghai）。[范围](updater-audit-2026-11-03/scope.md)。本次为用户自有 APK 的更新故障调查，未修改线上发布状态。

确认两处发布流程问题：v1.0.14 发布为预发布版，但已安装客户端只查询正式版；且发布附件没有原生插件必需的 `update.json`。目前客户端的固定接口返回 v1.0.7，而不是 v1.0.14。上传 APK 成功和提供网页下载不代表已经满足手机更新协议。此前发布验证遗漏了这条链路。

## 证据与结论

| 证据 | 观察 | 结论与处理路径 |
| --- | --- | --- |
| E-01：[UpdateRepository.smali](updater-audit-2026-11-03/UpdateRepository.smali)，check() 第 822 行起 | 固定请求 `/releases/latest`，第 918～933 行拒绝 draft/prerelease | F-01：现有插件不接受预发布通道；须让现有接口提供可接受的正式更新，或者在新客户端重新设计通道 |
| E-02：[release-state.json](updater-audit-2026-11-03/release-state.json) | `/releases/latest` 返回 v1.0.7，清单 versionCode=8；v1.0.14 为 prerelease=true | F-01 实际触发：已安装 v1.0.13 的 versionCode=14，大于接口返回的 8，不会出现新版 |
| E-03：上述原生方法第 955～1059 行与发布附件快照 | 必须先查找名为 `update.json` 的 Release 附件，再读取 schema、packageId、version、versionCode、apk、size、sha256；v1.0.14 只有 APK 和 SHA256SUMS.txt | F-02：只修改 prerelease 标志仍不足；还必须补齐插件所需清单。APK 内的 static/update-info.json 和 SHA256SUMS.txt 不能替代 Release 附件 update.json |
| E-04：[包内校验记录](bazi-classics-fix-2026-11-03/package-verification.json) 与原生 verify() 第 1565 行起 | v1.0.13/v1.0.14 签名相同；verify() 比较下载包与已安装包的签名，并校验大小、SHA-256、包名和版本 | F-03：两版的签名与递增版本号符合本次升级要求；不是 v1.0.13→v1.0.14 的签名迁移问题 |
| E-05：发布快照中的 dex_sha256 | 两个版本 classes.dex 相同 | F-04：本次只改网页资源，原生更新逻辑没有变化；即使手动装上当前 v1.0.14，也不会自动获得支持预发布通道的新原生逻辑 |

GitHub 官方说明 latest 接口只返回非预发布、非草稿的最新正式版：[Get the latest release](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)。这与原生方法及本次接口响应一致。

## 现有客户端实际经历的流程

打开更新页面 → 原生 check() 请求 latest → 获取 v1.0.7 及其 update.json → 得到 versionCode 8 → 与本机 versionCode 14 比较 → available=false。

因此不断点击检查或重新打开应用，无法使这个固定接口发现仍被标为预发布的 v1.0.14。自动检查还有时间节流，但手动检查没有这项五分钟限制，等待并不能解决上述两项发布配置问题。

## 修复方式

兼容现有 v1.0.13 的服务端修复路径：给 v1.0.14 补上正确的 Release 附件 `update.json`，核对其 APK 文件名、36,156,987 字节大小、versionCode 15、包名和 SHA-256，然后使该版作为正式版由 `/releases/latest` 返回。候选清单已生成在 [candidate-update.json](updater-audit-2026-11-03/candidate-update.json)，并核对与现有上传 APK 的名称、摘要、大小一致；**尚未上传该清单或更改发布通道**。

这条路径不要求为同签名的 v1.0.13 用户卸载应用，也不要求重新构建现有 v1.0.14 APK；仍须完成发布后接口、匿名清单下载以及手机端检查/下载/安装的验证。安装最终需要安卓系统确认。

正式通道原先保留在旧签名 v1.0.7。切换时须同步更新发布说明，区分旧签名用户与新签名用户；旧签名版仍不能无损覆盖安装新签名包。不能因为 v1.0.13 与 v1.0.14 同签名就假设所有历史版本都兼容。

长期应把“正式/测试”和“旧/新签名”通道明确设计到更新协议中，并给发布工具增加协议检查：缺失 update.json、APK 摘要不一致、目标通道不被客户端接受时，不能再将发布结果报告为手机更新可用。若保留预发布渠道，就需要支持它的新原生客户端；只推送 GitHub 源码或修改网页按钮不足以改变已经安装的 v1.0.13。
