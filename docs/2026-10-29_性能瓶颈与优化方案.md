# 造化元钥：性能瓶颈与优化方案

日期：2026-10-29。对象：本地整改后的开发版本，Git 基线 `a419219`。本轮仅测量和制定方案，没有修改 APP 业务代码，也没有发布安装包。

## 结论

优先优化**紫微运限计算、首盘预加载和大草稿集合的同步保存**。目前不能将主要卡顿归因于切盘动画：预热后切盘的页面隔离已起作用，隐藏盘面在本轮切换中没有重复渲染。若先重写动画或单纯提高刷新率，会绕开已经测到的主要瓶颈。

实际发现的最高优先级问题是：**切换紫微流日时，为生成列表文字，反复计算完整运限，并且不同用途共享的缓存会发生重复计算。** 浏览器降速样本中，一次日期更新耗时达到秒级。

## 测试条件与证据

- Chrome 140.0.7339.210，独立无头浏览器，430×932 页面尺寸，CPU 4 倍降速。
- 本地 HTTP 预览；关闭浏览器缓存，预览服务器使用 `no-store`。网页计时不包含安卓原生壳启动，HTTP 传输也不能等同于 APK 内置资源加载。
- 使用新建的合成命例；没有编辑真实用户资料。笔记压力样本均为自动生成，结束后删除了测试存储。
- 当前没有连接的安卓模拟器。本轮结果用于定位和优化排序，**不是安卓真机的耗时、耗电或 120 帧验收结果**。
- 常规耗时测量关闭了 CPU Profiler；另保存一次开启 Profiler 的采样，仅用于函数归因，不能混用其总耗时。

### 笔记压力测试

每个场景执行 12 次输入事件；当前编辑文本约 2,000 字符，其他合成草稿每份约 10,000 字符。测试调用现有真实输入处理函数并执行浏览器本地存储写入。

| 其他草稿数 | 草稿集合大小 | 输入处理耗时中位 | 最大 |
|---|---:|---:|---:|
| 0 | 约 2,111 字符 | 0.2ms | 0.6ms |
| 50 | 约 504,301 字符 | 6.9ms | 8.1ms |
| 200 | 约 2,011,001 字符 | 22.9ms | 34.0ms |

这证明问题随**未保存草稿集合**增大而加重，并非说明每个用户当前都有 200 份草稿。正常保存后草稿会删除，不能把正式笔记总数直接等同于草稿数。

## 瓶颈及具体优化

### P1-1：紫微列表用完整运限计算生成简单文字

位置：`dist/static/js/fivearts-ui.js:1082` 起的 `renderZiweiFlows()`。

当前为大限、流年、流月、流日、流时生成整组列表，其中流年、流日、流时的部分项目只是读取干支，却逐项调用 `getCachedHoroscope(...).yearly/daily/hourly`。一次日期变化会重新构造这些数据。本轮实际记录到 24～54 次 `chart.horoscope()` 调用。

方案：

1. 将列表的“显示数据”和当前选中盘面的“完整运限数据”分离。
2. 年、日、时列表所需干支尽量采用轻量计算；只有实际选中的日期、时辰和层级才计算完整星曜与四化。
3. 大限列表按命盘缓存，流年列表按所属年份区间缓存，月/日列表按农历年、月份和闰月状态缓存，时列表按日期及换日规则缓存。
4. 改变同月日期时更新选中项与时列表，不重建大限、流年和整月流日。

风险：紫微的晚子时、闰月分段与其他体系规则可能不同。不能直接用八字的午夜规则替换紫微时列表。优化前后必须逐项比对列表文字和实际命盘输出。

验收目标：同月日期切换不再触发几十次完整运限计算；计数预算为当前实际选中运限所需的 1～2 次。具体能否达到此预算，以输出一致性和测量为准。

### P1-2：紫微引擎反向查词每次扫描语言表

位置：`dist/static/js/fivearts-engine.js` 中压缩名 `Vr`，导出的反向转换函数为 `kot`。

当前逻辑包含嵌套 `Object.entries()`，逐个语言、逐个翻译项查找对应键。CPU 采样中该函数自身采样累计约 5.02 秒，是该轮最靠前的 JavaScript 耗时项；语言格式处理和资源查找也位列前部。这个数值来自开启 Profiler 的独立采样，不应拿来替代前表中的常规耗时。

方案：加载资源时建立反向索引，或按“输入文字＋类型过滤条件＋语言资源版本”进行缓存；对重复星名、宫位名、干支查找直接命中结果，减少全表扫描及临时数组分配。

风险：原函数存在别名优先级、过滤条件和首次匹配顺序。索引必须保留这些语义，不能因不同语言同名而改变返回值。

验收：对使用到的星曜、干支、宫名及简繁等资源做原函数/新函数对比，再测 `horoscope()` 总成本和 CPU 调用占比。该项应先做，通常比改动排盘算法风险低。

### P1-3：自动预加载把隐藏盘面的大工作放到主线程

位置：`fivearts-ui.js:901` 的 `prepareNextPane()`，以及结果宿主的 `renderedTabs`。

当前会逐步把五盘全部标为需要渲染，即使用户仍停在八字。本轮默认八字时已经生成其他四盘的页面，其中紫微元素最多。初盘附近出现秒级长任务，CPU 采样同时指向紫微计算链路，说明后台预热仍能抢占交互。

方案：

- 先让默认盘稳定显示，再在确有空闲预算时预备相邻一盘；不立即把其余盘全部挂载。
- 将计算准备与 DOM 挂载分开，避免“预计算”顺带渲染整张隐藏命盘。
- 用户开始滑动、点击或输入时取消低优先级预热；将工作拆成可让出主线程的步骤。
- 如果优化后的单次计算仍无法满足预算，再评估 Worker。Worker 应传输入及普通结果数据，不直接传带方法和循环引用的 chart 对象。

`requestIdleCallback` 本身不会把计算移出主线程；超时后仍可能在繁忙时执行，见 [MDN 说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback)。因此仅把当前函数放进 idle 回调不足以解决问题。

验收：默认盘可交互阶段不出现由非当前盘预热产生的秒级长任务；首次切到相邻盘也不能出现明显空白。必须同时测首次访问与重复访问，防止只把卡顿从启动移到第一次切盘。

### P1/P2-4：每次输入都序列化并写入整份草稿集合

位置：`paper-forest-details.js:140–153` 附近的字段观察与 `changeNote()`。

输入时读取、解析所有草稿，更新当前草稿，再序列化和同步写入整个集合。结构化字段观察还会序列化字段数组。草稿越多，单次输入处理成本越高；本轮合成大集合中已达到 22～34ms。

方案分两步：

1. 将当前草稿保持在内存，合并短时间内的连续输入，避免每次都读取和解析全集合；确保导航、明确保存时能够等待持久化。
2. 将正文和字段草稿按命例分别存储，优先评估 IndexedDB 的异步事务，避免修改一份草稿却写入所有草稿。保留旧格式迁移、备份恢复与损坏数据保护。

不能仅加一个 300ms 防抖就声称草稿不会丢失。系统直接终止进程时不保证触发退出事件，界面只能在事务提交后标记已持久化，明确保存应等待提交。

验收目标：在同一压力样本下，输入事件同步处理 P95 低于 4ms；存储提交与输入分开记录；重启恢复、并发修改与写入失败测试全部通过。

### P2-5：运限缓存粒度与容量不匹配

`getCachedHoroscope()` 的每个命盘缓存最多 80 条，采用插入顺序淘汰；命中时不调整顺序，实际上不是 LRU。日期列表和选中盘面共用它，生成列表会挤占已缓存的运限。与此同时，`chart._cachedFlowRows` 没有显式容量限制，本轮随着访问日期增长到 10 条。

方案：先拆分数据用途，再给不同缓存设置明确键和容量；限制 `_cachedFlowRows`，保留当前及邻近日期/月份。不要只把 80 调成几千，这会增加内存而保留多余计算。缓存键应包含命盘及相关历法规则，避免复用错盘。

本轮内存读数有垃圾回收波动，**没有证明存在永久内存泄漏**。缓存无上限是代码事实，长期保留内存的量仍需通过 GC 后快照验证。

### P2-6：启动资源和隐藏阅读 iframe 提前加载

静态入口直接引用脚本原始大小合计约 3.52MB，包括约 1.00MB 的五术引擎和 0.57MB 的题库数据；另有约 2.99MB 的公共业务 chunk。首次浏览器测量还加载了离屏的 `static/newguji/index.html`，带出其脚本、样式与远程 jQuery。iframe 清单确认该阅读页当时没有显示。

方案：

- 题库数据到进入题库前再加载。
- 阅读 iframe 在用户实际打开解说时创建/设置地址；隐藏页面不提前运行完整阅读应用。
- 分析五术引擎按需加载的可行性，但必须修正 `FiveArtsUI` 对引擎全局对象的加载依赖，保留脚本执行顺序和单例加载 Promise。
- 对公共 chunk 的拆分放到恢复模块化工程之后，不优先对压缩产物做大范围手工拆包。

这些建议针对启动解析和运行成本。APK 中体积大的图片若根本没被加载，删除它们主要影响安装包大小，不能直接当作切盘提速方案。

### P2-7：基础八字接口的重复请求需要进一步核对

本轮创建命例过程中，同一 `getbasebz8.php` 地址出现两次请求，耗时约 215ms 和 155ms。采样未保留原始请求参数，因此**尚不能认定它们完全重复或可直接合并**。当前结果准备约 3.95 秒，说明只优化网络不能解释或消除全部等待。

方案：记录去敏后的参数摘要，区分真太阳时校正、提交排盘和重复点击；仅对参数与规则完全相同的并发请求合并。成功结果缓存需带历法与规则版本，不跨不同时间输入混用。

## 不应优先改动的部分

1. **普通切盘的组件隔离：**10 次预热后切换，仅记录到宿主更新，没有其他盘面的重复渲染。流日更新则只触发紫微页面的更新。现有隔离应保留，不能为了“优化”恢复到所有页面共用一次大渲染。
2. **1 秒首页时钟：**有可见性和分钟变化检查，未测到它是本轮主要长任务来源。后续可检查 keep-alive 激活/停用时的定时器生命周期，优先级低于秒级运限计算。
3. **15 分钟更新检查：**本轮没有证据证明它是主要交互瓶颈，不需要先删功能。
4. **箭头清晰度：**当前用独立 SVG、非缩放描边及尺寸观察，不应通过整体降分辨率或模糊缓存来换取动画帧数。

## 实施顺序

| 顺序 | 工作 | 预期收益方向 | 主要风险 |
|---|---|---|---|
| 1 | 反向查词索引与结果一致性测试 | 降低紫微重复计算的基础成本 | 别名、类型过滤及多语言冲突 |
| 2 | 运限列表轻量计算、分层缓存 | 消除每次日期刷新几十次完整运限调用 | 晚子时、闰月、运限显示规则 |
| 3 | 按需预热与分步调度 | 减少默认盘可交互阶段的主线程阻塞 | 首次切盘变慢或闪空白 |
| 4 | 草稿按命例存储、异步持久化 | 大草稿集合下改善输入延迟 | 数据迁移、异常恢复、最后编辑保全 |
| 5 | 阅读/题库按需加载 | 降低启动资源解析和隐藏页面开销 | 旧阅读跳转、首开加载及离线资料完整性 |
| 6 | 请求归并与真机性能回归 | 减少重复等待，确认实际帧表现 | 错误缓存不同起盘参数 |

前两项完成后应先重新采样，再决定是否需要 Worker。此处的收益是方向与验收目标，没有把尚未实现的提速百分比当成承诺。

## 验收方法

- 固定相同资料、历法规则、设备、WebView、温度状态和数据规模；分别测试冷启动、首次切盘、预热后切盘、连续流日、快速输入和后台恢复。
- 在同一浏览器降速条件下，先把流日更新中位耗时目标设为低于 200ms、争取低于 100ms，并测 P95；目标是否满足必须由实现后的数据说明。
- 主线程长任务应显著减少。Long Tasks API 只记录 50ms 及以上任务，见 [MDN](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming)；“没有 50ms 长任务”仍不等于能稳定达到 120 帧。
- 120Hz 设备单帧总预算约 8.33ms。应在真实 120Hz 安卓设备用帧时间和掉帧数据验收，区分屏幕刷新率、rAF 频率和实际呈现帧数。本轮浏览器约 60Hz，不能据此宣称已经或无法达到 120fps。
- 任何计算优化都必须跑现有 28 项回归，并新增运限列表前后对照；任何草稿优化都必须验证正文、结构化字段、备份恢复及写入失败。
- 缓存检查按连续访问日期数、命例数记录，并比较 GC 后的保留对象。不能只凭一次堆内存上涨认定泄漏。

建议第一批实施范围：**反向查词索引＋运限列表与缓存拆分＋预热调度**。它们直接对应本轮最明显的秒级等待，之后再处理大草稿输入和启动资源。
